# OCR 服务部署运维说明

## 运行要求

- Python 3.11
- CPU 或支持对应 CUDA 版本的 NVIDIA GPU
- 独立虚拟环境，不与 ASR 的 PyTorch/FunASR 环境混用
- 生产环境使用一个 worker，避免重复加载模型

## Linux CPU 部署

```bash
cd /www/famm/ocr-service
python3.11 -m venv .venv
.venv/bin/python -m pip install --upgrade pip setuptools wheel
.venv/bin/python -m pip install --no-cache-dir -r requirements-cpu.txt
test -f .env || cp .env.example .env
mkdir -p model_cache tmp logs
```

生产 `.env` 建议：

```text
OCR_HOST=127.0.0.1
OCR_PORT=8898
OCR_DEVICE=cpu
OCR_AUTO_LOAD=true
OCR_ENABLE_MKLDNN=false
OCR_MODEL_CACHE_DIR=model_cache
OCR_TEMP_DIR=tmp
```

启动：

```bash
.venv/bin/python -m uvicorn app.main:app \
  --host 127.0.0.1 \
  --port 8898 \
  --workers 1
```

Java 后端和 OCR 服务位于同一台机器时，只监听 `127.0.0.1`，不要向公网开放 8898。

## 启动顺序

```text
1. OCR 服务
2. Java 后端
3. 前端联调
```

## 健康与业务验证

```bash
curl --fail-with-body http://127.0.0.1:8898/v1/ocr/health
curl --fail-with-body -X POST http://127.0.0.1:8898/v1/ocr/warmup
curl --fail-with-body -X POST http://127.0.0.1:8898/v1/ocr/recognize \
  -F "image=@tests/test.jpg"
```

`warmup` 后确认健康响应中的 `model_loaded` 为 `true`。

## 常见问题

- 首次请求慢：生产设置 `OCR_AUTO_LOAD=true`，或部署后调用 warmup。
- CPU oneDNN/PIR 错误：保持 `OCR_ENABLE_MKLDNN=false`。
- 重复下载模型：确认 `OCR_MODEL_CACHE_DIR` 可写且持久化。
- 内存过高：确认只运行一个 worker，且没有重复启动进程。
- 端口变更：同步修改 Java 后端的 `ocr.local.base-url`。
